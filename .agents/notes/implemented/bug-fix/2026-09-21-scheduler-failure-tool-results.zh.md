# Agent Note: 调度器失败仍为每个已记录的 tool call 配对结果

Status: implemented

[English](2026-09-21-scheduler-failure-tool-results.md) | 中文

## 问题

模型工具调用在日志中按顺序记录两次：assistant 消息携带 `tool_use` 块，step 追加 `tool/call` 事件。只记录调用而不记录其结果，并不只是留下一个未完成的 step。DeepSeek Messages 请求会遍历日志，拒绝 assistant 轮的 `tool_use` id 未被紧随其后的 user 轮全部解析的历史，而且这个检查发生在构建请求阶段、任何网络调用之前。因此只要有一个未配对的调用，该 session 之后的每一轮都会失败，无论模型与连接状态如何。

agent loop 的中止路径早已知道这一点。它用合成的 `isError` 结果为每个未调度的调用作答，使日志保持有效 transcript。调度器失败路径却没有：`startCall` 追加 `tool/call` 后等待 `TOOL_RUNTIME_SCHEDULER.prepare`，而该调用抛出后会穿过该组的失败 `catch` 向外传播，始终没有写入任何结果。对同一个已记录的调用，中止与失败产生了不同的持久化后果。

两个 `dsh-tools` 模块实例的冲突使这条路径在源码启动中对每次工具调用都可达，但该缺口与它无关：任何来自调度器所拥有的准备、调度或终结阶段的抛出都会走到这里。[该冲突的解决方式](2026-09-21-workspace-package-entry-agreement.zh.md)是另一项决定。

## 决策

step 在调度器失败向外传播之前收束其已记录的调用。两种情况由两个错误码区分，二者都在错误名 `ToolSchedulerError` 之下，并以 cause 链作为模型可见文本：`TOOL_SCHEDULER_FAILED` 表示该调用已被记录、可能已到达主体，因此结果未知；`TOOL_SCHEDULER_FAILED_BEFORE_DISPATCH` 表示该调用因失败而从未启动。

结果由既有的有序路径写入，而不是在失败点写入。`startCall` 本就在等待准备之前记录自己的 `tool/call` seq，现在把 `prepare` 的抛出锁存下来，而不是任其未配对地逃逸。该组的失败 `catch` 先排空在途调度，再通过与常规路径相同的 `commitReady` 提交所有已结算的结果，因此确实产生了真实结果的调度会保留它。此后才按模型顺序为其余调用作答。在失败瞬间写入结果更简单，但会出错：结果必须与已结算的同批调用一起按模型顺序提交。

`executeToolCalls` 同样会收束失败未曾到达的后续组中的调用。这是正确性要求，而非锦上添花：assistant 消息只追加一次并列出每一个调用，因此后续组的调用与失败组的调用一样未配对。

失败仍以原始错误到达轮次边界，因此 `turn/end` 保留 `{ kind: 'error' }` 与原始消息，而不是合成的工具错误。

## 备选方案

**扩展中止路径而不新增失败路径。** 中止是另一种结果，有其自己的错误码与信号语义；把调度器故障报告为 `ABORTED_BEFORE_DISPATCH`，等于对模型与回放日志声称是用户取消，而实际是插件失败。

**在 `startCall` 的抛出点直接追加合成结果。** 这是对需求最直观的解读，但一旦同一并行池中的兄弟调用先结算，它就会颠倒结果顺序。

**丢弃该组已结算的结果并为所有调用合成。** 日志仍然有效，但丢弃了已完成的工具工作，并把成功报告为失败。

**在下次加载时修复日志。** 崩溃修复只收束**处于打开状态**的尾部轮次。已经提交了 `turn/end` 的失败不属于打开的轮次，因此修复不会产生任何事件；在此变更之前以此方式损坏的 session 将保持损坏。

## 后果

调度器故障现在只让一轮失败，而不再毁掉整个 session。持久化日志为每个已记录的调用保留一个结果，因此后续轮次可以据此构建请求，模型也能看到哪些调用执行过。

step 可能报告它并未观察到的工具结果。`TOOL_SCHEDULER_FAILED` 的准确含义正在于此：该调用可能已到达主体。模型可见文本携带 cause 链，并不声称工具没有运行。

在此变更之前已经损坏的 session 不受其影响，必须替换；崩溃修复所收束的那种 `未配对调用` 形态，在已结束的轮次上从来不可达。

`packages/core/agent-loop/tests/tool-calls.spec.ts` 包含三个用例：已排空的池中发生准备阶段抛出、前置独占屏障失败导致后续组从未运行，以及并发上限受限、只记录过第一个调用的组。它们合计覆盖了两个错误码与两条收束路径。每个用例都断言错误仍传播到 `turn/end`、assistant 消息列出的每个调用都被恰好作答一次且没有为未记录的调用写结果，并且派生历史满足 provider 规则——assistant 轮的工具调用都被紧随其后的 user 轮解析。未新增已提交 session 快照；对于难以通过 shipped profile 复现的路径，派生历史断言已覆盖回放要求。

[协作式工具取消决策](../architecture/2026-07-19-cooperative-tool-cancellation.zh.md)仍拥有中止错误码与注册表边界；本记录只拥有调度器失败时如何处理它已经记录的调用。
